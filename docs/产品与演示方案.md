# 产品假设：方舟食境

一句话：用影石全景影像，把自助餐厅变成可以探索和找餐的空间菜单。

## 为什么先做这一小段

待验证假设：第一次进入陌生自助餐厅的人，需要反复绕场找菜、辨认菜牌、询问工作人员。传统菜单没有“在哪里”，纯全景没有“这是什么”，单独聊天推荐也不直接指向真实餐台。

拟验证的创新：把“影像证据、菜品语义、空间点位、可行走路径”绑定在同一份场景中。现场影像发生变化时更新对应区域；每道菜能追溯到采集时间和原图。创新价值需要通过实验和竞品核验，不宣称全球首创。

主用户先选第一次到访的住客；餐厅工作人员是菜单确认者。第一版不做人体热量判断，不把整个度假村高精重建作为交付前提。

## 最小真实闭环

1. X5 采集一个餐区。
2. 拼接并重建，得到一个可浏览的真实小场景。
3. 识别 3–5 张菜牌，人工核实后将菜品锚定在餐台。
4. 用户选择“南京风味 / 蔬果 / 甜点”等偏好。
5. 在真实场景中高亮相关餐台并展示通道路线。
6. 找到菜品后完成任务，记录任务耗时和误找次数。

本版先交付交互、参考园区、资产查看器、真实 OSC 适配。AI 识别、场景训练、人工核实与现场实验尚待数据和设备，不作为已完成功能参赛陈述。

## 需求验证（建议 5 位用户）

每人分别完成两个同等难度的找餐任务，一个使用现场常规信息，一个使用原型。交替安排两种方式的顺序，减少先熟悉环境带来的优势。记录：

- 起止时间与是否成功。
- 走错餐台次数、询问工作人员次数。
- 是否读懂菜品信息。
- 对定位准确性和使用意愿的简短反馈。

先问开放问题：“刚才找餐最费事的步骤是什么？”避免先暗示对方应当需要本产品。结果样本小就如实呈现，不把 5 人测试描述为统计显著证明。

## 三分钟比赛演示

- 0:00–0:25：用户进入陌生餐厅的具体任务与已观察问题。
- 0:25–0:55：旋转仙林园区参考模型，进入实拍餐区。
- 0:55–1:30：选三种食物偏好，出现菜牌证据与餐台锚点。
- 1:30–2:00：展示真实可走路线和找餐任务。
- 2:00–2:30：展示一小段影石原始采集 → 拼接 → 重建 → 网页的真实证据链。
- 2:30–3:00：现场验证结果、已知不足与可扩展方向。

如果真实重建未完成：明确演示 ERP 全景 + 点位流程，另展示参考体块；如实标出 3DGS 部分的实际进展。不要将规划模型或单张全景误报为真实现场重建。

## 优先级

P0：可访问的网页、一个真实餐区、三道真实菜品、至少一次设备与处理联调、用户任务记录。

P1：更精确建筑外观、更多餐台、坐标配准与场景更新。

P2：跨楼层全园区导航、实时客流、营养估计、无人机大范围重建。这些不能拖垮 P0。
