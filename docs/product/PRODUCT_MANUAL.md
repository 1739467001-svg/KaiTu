## 把场地影像，变成可用的服务。

开图是一套面向景区、度假村与文旅街区的全景内容运营原型：从现场采集开始，让游客看懂空间、安排逛吃，再让场地方看见服务转化。

> 一句话介绍：用影石全景采集场地，把影像接上 AI 逛吃与商家服务，让一次浏览有下一步。

### 我们首先解决什么

场地往往有宣传片、平面地图和餐饮菜单，但三者彼此割裂。游客看完风景仍不知道怎么走、在哪吃；运营人员每次换活动、换商家都要重新组织内容。开图把“场景—点位—行程—餐饮服务”放进同一套可更新的内容结构。

采集空间 → 浏览与理解 → 安排逛吃 → 到店与反馈

### 核心产品是影像工作台

三维场景是体验入口，影像工作台是供给工具，AI 逛吃是消费入口，商家运营是价值验证工具。工作台把素材导入、质量检查、处理状态、现场校准和资产交付连接起来；长期竞争力应来自更短的交付时间、更稳定的资产质量，以及可复用的场地数据结构。

### 适合比赛的切入点

以 Club Med 南京仙林度假村为首个采集试点，再用栖霞山、老门东验证不同业态的内容复用。X4 Air 的全景采集适合低门槛记录公共空间，“一份影像，多种取景与服务入口”可被现场演示。

> “让任意物理场地 30 分钟上线”保留为产品目标。当前没有覆盖任意场地的验证，不把它写成已达成的承诺。

## 谁来使用，谁愿意付费？

优先服务有明确运营主体、有固定餐饮服务、有持续内容更新需求的中小型文旅场地。

| 角色 | 实际任务 | 开图提供的价值 |
| --- | --- | --- |
| 游客 / 亲子家庭 | 出发前了解环境；到达后安排休息、拍照与用餐 | 看实景；选择现成行程；按人数、时间和预算选择餐饮组合 |
| 景区 / 度假村运营 | 降低重复介绍成本；更新活动；推广餐饮和体验服务 | 可维护的空间点位与内容；面向游客的统一入口 |

### 首个付费客户画像

建议先接触单一运营方管理的度假村公共区或小型文旅街区，覆盖 5–10 个关键点位和 3–5 家合作商户。决策链短、内容边界清楚，比一开始复制整个城市更容易验证。

### 游客价值如何证明

试点记录“找到目标服务所用时间、完成行程选择比例、真实到店比例”；访谈游客是否更容易理解入口、步行关系与用餐位置。体验是否漂亮只是起点，能否帮助游客做决定才是结果。

### 运营价值如何证明

记录从采集到可交付的实际分钟数、每次更新的人时、有效素材比例和服务信息错误数。餐饮转化应按独立券号与去重到店统计；当前网页中的示例底稿和套餐面额不计为真实经营结果。

以上为待访谈验证的需求假设，尚未声称已有签约客户、付费订单、客流增长或市场份额。

### 实拍全景能做什么

一张 2:1 全景照片可以提供固定视点的 360° 浏览和不同方向取景。它不能恢复被遮挡的建筑背面，也不能产生真实的自由移动视差。印度门模型是人工参照照片建立的几何解释，不是单张图自动重建。

### 可商用化的素材策略

开源许可照片保留作者、来源、修改说明及许可；取景导出继承相应图像许可。本次找到的两个南京旧全景播放器均已无法打开，产品保留检索记录和原页链接，不加载空白播放器。正式客户交付以自采或明确取得授权的素材为主，并保留原片和授权记录。

完整出处与许可：项目 public/ASSET_LICENSES.md。两个南京旧全景暂不可播放；影石实拍样例和两张对照照片已本地打包。

## 你负责现场，我负责把素材变成产品。

先完成一个小区域的真实闭环，再扩大建模范围。不要一次拍完整园区后才第一次检查素材。

| 阶段 | 现场同伴具体操作 | 线上处理与验收 |
| --- | --- | --- |
| 准备 / 5 分钟 | 确认公共拍摄范围；擦净双镜头；检查电量与存储；使用相机支持的稳定参数 | 在工作台开始记录；先传 20 秒测试片验证文件、拼接和清晰度 |
| 主采集 / 3–5 分钟 | 优先入口、主路径和餐饮入口；慢走闭环，保留明显平移与连续重叠 | 检查画面清晰、曝光稳定；规划可作为全景节点的片段 |
| 补拍 / 5–10 分钟 | 入口正面与斜侧面、导览牌全图及局部、楼层图、赛事布展、菜单和价格牌 | 识别建筑与服务点；将可信信息录入结构化点位并关联照片 |
| 校准 | 记录至少 3 个固定锚点和 1 段实测距离；标记楼层、方向、文件名 | 核对相机方向、地面、尺度和通行关系；未校准项目保持待确认 |
| 交付 | 保留原始文件、配对和分段；核对素材清单 | 导入拼接产物；必要时外部重建；浏览验收并导出清单 |

### 设备参数怎么用

X4 Air 官方产品信息包含 8K / 30 fps 全景、165 g 机身、单镜头 4K / 60 fps。全景视频用于记录空间；单镜头模式可补门牌、菜单和细节。实际采集参数应以赛事指南、设备菜单和现场测试为准。[1]

### 最有价值的补充资料

拍清“入口怎么进、楼层怎么连、服务点在哪里”。餐饮需要菜单全图、套餐价格、营业时段与商户确认；过敏原不能仅靠照片推断。夜间水幕单独拍摄与标记，不混入白天静态重建序列。

> 建议文件夹：场地 / 日期 / 原片、拼接、细节、锚点、授权。原片不改名覆盖；用表格把照片文件名与锚点编号对应起来。

## 把影石能力接入一个可替换的处理链。

影石设备负责高质量采集；网页负责浏览与服务；重计算在独立任务中执行。

X4 Air 原片 → Studio / SDK → 全景浏览 → 可选 3DGS

| 环节 | 当前状态 | 正式接入方式 |
| --- | --- | --- |
| 设备控制 | 本地 OSC 桥接可检测、开始与停止；模拟协议测试已覆盖；X4 Air 未实测 | 现场电脑连相机 Wi-Fi；按赛事 SDK 与机型兼容清单验证，不能从公网网页直接连接相机局域网 |
| 拼接与导出 | 浏览器不解析原始 INSV；引导使用 Studio 外部处理 | 有 SDK 授权后将 Media SDK 包装为独立任务适配器，产出统一 ERP 文件和处理记录 |
| 检查与抽帧 | 云端 CPU worker 可检查素材并使用 FFmpeg 抽帧 | 素材状态、错误与输出进入任务队列；重试有记录，避免伪装成成功 |
| 几何重建 | 预留外部 GPU 流程；并非现成端到端重建服务 | ERP 转多视角透视图，求解相机位姿，再做 3DGS；需独立 GPU、实拍和质量验收 |
| 网页交付 | Three.js 全景与程序化模型；Spark 显示 PLY / SPZ / SPLAT | 统一资产 ID、来源、尺寸、姿态与状态；替换视觉层时保留 POI 与餐饮服务层 |

### 为什么不能把全景当成普通照片直接重建

ERP 图像是球面投影，传统针孔相机求解不能无条件直接套用。应处理投影与相机内参，保留多视角重叠；反射水面、移动游客、纯色墙体和夜间运动会增加重建难度。当前只声明可导入完成的高斯资产。

SDK 二进制、授权凭据、机型联调、自动 GPU 重建尚未完成。界面已预留清晰工作步骤，但不将 OSC 桥接或操作说明写成 SDK 已集成。

## 先给可信选择，再增加生成能力。

AI 的任务是把游客的表达映射到场地真实可提供的服务，而不是自由编造餐厅、价格或路线。

一句需求 → 识别与筛选 → 目录内方案 → 约束校验

### 当前可直接使用的两层能力

第一层是 9 个内置策划行程，点击即可演示。第二层是本地朴素贝叶斯意图识别与规则筛选，结合人数、餐饮预算、停留时间和禁忌约束选择已有方案。界面明确显示是内置示例或本地模型。

### 实时模型如何接入

云服务器配置兼容接口地址、模型名和 API 密钥后，在影像工作台连接后台。实时模型只能返回目录中存在的方案 ID，服务端再核对目的地、预算、人数等条件；没有匹配时应返回无结果，不将模型生成价格写入订单。当前没有配置生产模型密钥，因此不声称已完成真实供应商调用验收。

| 内置示例输入 | 可展示的输出 | 实际用户价值 |
| --- | --- | --- |
| 一个人，45 分钟，预算 22 元，想尝小吃 | 老门东短行程 + 甜品示例 + 相关点位 | 降低决策成本；看清时间和餐饮预算 |
| 想在栖霞山赏秋，坐下喝杯茶 | 沿湖秋色行程 + 茶点示例 | 把拍摄点与休息、餐饮连接起来 |
| 两个人想在仙林湖边看日落喝茶 | 日落行程 + 双人下午茶示例 | 将场景浏览连接到场地可提供的服务 |

### 下一阶段的 AI 影像能力

可增加菜单 OCR、门牌识别、素材清晰度与覆盖缺口提示、自动生成待确认 POI。所有识别结果须经运营人员确认后发布；不同楼层、营业状态、过敏原、支付与可达性等事实不交给模型自行猜测。

> 差异化方向：影像资产与结构化场地服务绑定。模型可以替换，可信点位和运营目录可以持续积累。

| API | Bearer 访问密钥、项目与素材管理、任务提交、AI 适配器 | 组织 / 项目角色、按用户隔离、审计日志与限额 |
| 数据库与文件 | SQLite 项目 / 任务状态，持久卷存放上传文件 | 多租户采用 PostgreSQL、对象存储、签名访问链接 |
| CPU Worker | FFmpeg 检查和抽帧；任务领取去重；错误显式记录 | 队列服务、重试策略、容量监测与任务告警 |
| GPU Worker | 外部流程；网页只导入结果 | 独立 GPU 池运行位姿求解和重建，按任务计费 |
| 商户交易 | 浏览器本机演示账本 | 正式上线需服务端券账本、幂等核销、商户鉴权与支付渠道 |

### 部署要点

Docker 构建包含 public 目录中的实拍、插画和说明书；运行 Node 服务并挂载持久卷，CPU worker 单独运行。按 .env.example 配置访问密钥与可选 AI 参数；密钥仅放在服务端，不提交到 Git。生产入口使用 HTTPS，按部署文档配置反向代理。

### 性能与画质

实例化植被、重复材质合批减少绘制开销；水体反射、PBR 与夜景发光改善环境层次。高画质可启用 GTAO，流畅模式降低后处理负担。打开实景资料夹时暂停本地三维渲染。实际帧率取决于设备，应在路演电脑上验收。

当前静态发布站不等于完整 API / GPU 服务已经上云。云架构可部署，真实服务器运行、域名与模型凭据仍需在目标环境验证。

### 暂不优先靠抽佣

先验证是否产生增量到店，再讨论套餐成交分成。抽佣依赖真实支付、退款、结算和归因，当前原型尚不具备。先收明确范围的上线服务费，更容易解释价值和控制成本。

示例试点如收入 2,000 元、直接交付成本 1,200 元，贡献为 800 元；同样不代表净利润。正式商业计划必须用真实工时、获客成本、续费率与服务器账单更新。

## 用一个真实区域完成第一笔验证。

把“做完整个园区”的任务改成“交付可复用的小区域”，同时记录能证明价值的数据。

| 时间 | 目标与负责人 | 验收口径 |
| --- | --- | --- |
| 第 1–2 天 | 现场同伴拍入口与公共路径；线上完成全景接入、点位和目录校对 | 至少 5 个可辨认节点；每个节点有来源、位置说明与责任人 |
| 第 3–7 天 | 运营方确认 3 家商户信息；邀请 10–20 名游客完成任务 | 观察找路 / 找服务耗时；记录错误、无法理解的描述与缺失信息 |
| 第 2 周 | 完成一次活动或菜单更新；比较更新前后工作量 | 记录实际更新人时；核对资产版本与服务信息一致 |
| 第 3–4 周 | 接入服务端券账本后做小范围商户试点 | 使用去重券号统计真实到店；不混入演示底稿；复盘是否愿意付费 |

### 建议先设目标，再测量

采集到首个可浏览区域目标 30 分钟；有效节点覆盖率目标至少 90%；运营内容确认率目标 100%；完整演示链路目标连续成功 5 次。这些是建议试点验收阈值，不是当前已经测得的指标。

### 角色分工

现场同伴负责设备、允许拍摄的范围、路径与原片、导览牌和实测数据。线上开发负责拼接产物检查、模型和全景浏览、点位结构、界面与部署。场地方负责营业与通行信息确认。餐饮商家负责价格、库存、套餐条款和过敏原信息。

### 上线前的最小闭环

明确一名场地内容负责人；确定拍摄与素材使用范围；每个服务点有可信来源；游客能完成一个任务；运营方能修改一条信息；交付资产有备份、版本和回退方法。

> 最强的下一次路演证据：现场采集计时记录 + 一个真实入口全景 + 一条经商户确认的餐饮服务 + 一次可核验的用户测试。

## 有边界的产品，比夸大的承诺更可信。

回答时先说已实现的结果，再说下一步需要什么证据。

### 为什么不只是一个漂亮的 3D 网页？

三维展示只是入口。我们把素材采集与交付、游客行程、餐饮服务和商户核销组织成可操作的链路。核心要验证的是场地内容上线和更新成本能否下降，以及推荐是否带来可核验的到店。

### 为什么一定要用影石？

全景采集能在同一个拍摄点保留多个方向，适合入口、街巷与公共空间的快速记录，也方便事后取景。本版已使用可验证为影石 ONE RS 的公开授权全景；X4 Air 是现场采集方案，尚待比赛设备实测，不能混淆两者。

### 这些模型是真实扫描吗？

南京场景和印度门额外模型目前是照片与公开资料参考的人工模型。照片是实拍，全景是固定视点浏览；模型不具备已测量的几何精度。网页可加载外部完成的 3DGS 资产，但当前没有自采的南京 3DGS 重建成果。

### AI 在哪里？有没有真实大模型？

当前有本地意图识别和约束筛选，预置方案可离线演示。服务端已提供实时模型适配与输出校验；需要配置模型供应商凭据后联调。菜单 OCR、空间语义提取等列为下一阶段，不包装成已上线功能。

### 为什么客户会付钱？

假设客户愿意为更低的影像交付和更新成本、统一的服务入口、可验证的餐饮到店付费。我们先用单区域有偿试点验证，再推出订阅；当前没有把假设收入或演示券算成真实商业成绩。

### 素材是否可以直接用于商业客户？

本地公开授权照片需遵守各自许可；发现公开全景介绍页不等于获得可播放文件或原片商业复用授权。正式交付优先使用自采或书面授权素材，保留来源、用途与同意范围。AI 插画只作界面创意装饰。
